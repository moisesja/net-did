# Issue #109 — Observe WaitAsync-abandoned RPC tasks (did:ethr)

## Context

PR #108's hardening wraps did:ethr RPC/signer awaits in `.WaitAsync(ct)` so a token-ignoring client cannot hang a write past `WriteDeadline`. That gain stays — but `WaitAsync` **abandons** the underlying task rather than cancelling it. If the abandoned task later faults, nothing observes the exception and the finalizer raises `TaskScheduler.UnobservedTaskException` in the host: telemetry noise for hosts that hook the event (App Insights, Sentry), and a process kill for hosts opting into `ThrowUnobservedTaskExceptions`. Measured, not theoretical (probe in the issue). Severity: **Low** (no correctness/security impact) — matches the issue.

## Assessment (validated against source)

All 15 are `Task<T>`; no non-generic usages.

**Out of scope, with justification:**
- `Task.Delay(ReceiptPollInterval, ct)` (TransactionPipeline.cs:315) — `Task.Delay` observes its token natively; cancellation is real cancellation, nothing is abandoned.
- The resolver read path (`DidEthrResolver`) and all other DID methods — grep shows zero `WaitAsync` sites outside the three files above; their deadline handling passes `ct` directly, so faults are always observed by the awaiter.
- Changing the `WaitAsync` deadline semantics themselves — the issue explicitly says the robustness gain must stay. The deliberate "already-completed task wins over a canceled token" race handling (TransactionPipeline.cs:258 comment + explicit `ThrowIfCancellationRequested` re-checks) is preserved because the helper still returns `task.WaitAsync(ct)`.

## Fix (issue's suggested shape, as an extension method)

New internal extension, file `src/NetDid.Method.Ethr/AbandonableTaskExtensions.cs`, namespace `NetDid.Method.Ethr` (visible to the `Transactions`/`Deployment` child namespaces without new usings):

```csharp
internal static class AbandonableTaskExtensions
{
    public static Task<T> WaitAsyncObserved<T>(this Task<T> task, CancellationToken ct)
    {
        // WaitAsync abandons rather than cancels; observe a later fault so it cannot
        // surface as a TaskScheduler.UnobservedTaskException escalation in the host.
        _ = task.ContinueWith(
            static t => _ = t.Exception,
            CancellationToken.None,
            TaskContinuationOptions.OnlyOnFaulted | TaskContinuationOptions.ExecuteSynchronously,
            TaskScheduler.Default);
        return task.WaitAsync(ct);
    }
}
```

- `CancellationToken.None`: the observer itself can never be canceled away.
- `OnlyOnFaulted`: on success/cancel the continuation is *canceled*, and canceled tasks never raise `UnobservedTaskException`.
- `ExecuteSynchronously` + `TaskScheduler.Default`: no ambient-scheduler capture, negligible overhead (each site is a network round-trip anyway).

Then a mechanical swap at all 15 sites: `.WaitAsync(ct)` → `.WaitAsyncObserved(ct)` (respectively `token`). No behavior change on any non-fault path.

### Review round 4 plan — 2026-07-28 (maintainer re-review, PR #113)

#### Confirmed findings

1. **Task-level cancellation semantics are not identical to bare `WaitAsync`.** The async
   `AwaitObservingAbandonment` wrapper catches every `OperationCanceledException`. If a source
   task was pending when wrapped and later faults with an `OperationCanceledException`, bare
   `WaitAsync` returns a `Faulted` task with a non-null `Exception`; the wrapper instead returns
   a `Canceled` task with `Exception == null`. Source self-cancellation also enters the catch and
   creates observer state even though no source task was abandoned.
2. **The zero-allocation claim is false for pending, normally completing awaits.** Every such
   await currently creates the async wrapper task (measured at approximately 120 bytes per call).
   The XML documentation and CHANGELOG overstate the optimization by saying those awaits "pay
   nothing" / have "no extra allocation."
3. **The source guard remains lexically bypassable.** It applies its regular expressions one
   line at a time, so legal `.WaitAsync\n(ct)` and `.WaitAsync /* comment */ (ct)` calls evade the
   zero-bare-call assertion. The fixed 8/6/1 inventory also cannot detect an additional bare
   sixteenth dependency await.
4. **The PR description is stale.** It describes eager pre-abandonment observer registration,
   eight tests, the removed heap-retention oracle, and the old Ethr test count.
