# Issue #117 — did:ethr didDocumentMetadata `updated` / `nextUpdate`

## Context

The reference `ethr-did-resolver` populates `didDocumentMetadata.updated` (ISO 8601 UTC
block timestamp of the last applied change) on every resolution with history, and
`nextUpdate` alongside `nextVersionId` on historical (`versionId`/`versionTime`) queries.
NetDid emits neither, so the maintainer's planned metadata diff (issue #117, comparison
DIDs in the gist linked from the issue) diverges on day one.

**Root cause (confirmed):** `ResolveFromChainAsync` builds metadata with only
`VersionId`/`Deactivated`/`NextVersionId` — `src/NetDid.Method.Ethr/DidEthrMethod.cs:382-389`.
The Core model already has both fields: `DidDocumentMetadata.Updated` (`DateTimeOffset?`)
and `NextUpdate` (`string?`) — `src/NetDid.Core/Model/DidDocumentMetadata.cs:6,11`. No Core
change needed.

**Normative semantics (verified against the did:ethr spec Read section and
`resolver.ts` of the reference implementation):**
- `updated` MUST be the ISO date string of the block time of the latest applied update,
  *without sub-second resolution* (e.g. `2021-03-22T18:14:29Z`). Reference sets it whenever
  `versionId !== 0` (i.e. ≥1 applied event) — on current *and* historical resolution.
- `nextUpdate` MUST be the ISO date string of the block time of the next update; reference
  sets it whenever `nextVersionId` is finite (only possible on `versionId`/`versionTime`
  queries — same condition NetDid already uses for `NextVersionId`).
- Genesis documents (no applied events) omit `versionId`/`updated`/`nextVersionId`/`nextUpdate`.
- `deactivated` merges alongside these fields (a deactivated doc with history has both).

Severity: Medium (interop divergence, no security impact). Matches issue label `enhancement`.

## Out of scope (with justification)

- **Core model/serializer changes** — both fields exist and serialize; the
  `Updated: DateTimeOffset?` vs `NextUpdate: string?` asymmetry is the published Core API;
  changing it is a breaking change unrelated to this issue.
- **Other methods (`did:key`/`did:peer`/`did:webvh`)** — their metadata contracts are
  separate specs; webvh already emits its own version metadata.
- **W3C conformance suite** — `updated`/`nextUpdate` are method-specific resolver outputs,
  not DID-Core document statements.
- **Issue #120 interop fixtures** — the recorded-fixture harness is its own issue (blocked
  on the maintainer's DID list conversation); here I do a best-effort live diff only.
- **RPC error-shape hardening** — untouched; no new response *shapes* are parsed
  (`GetBlockTimestampAsync` already validates and is already used on both historical paths).

## Plan

### 1. Implementation — `src/NetDid.Method.Ethr/DidEthrMethod.cs` (single file)

All inside `ResolveFromChainAsync` plus one small private helper:

1. **Block-timestamp cache**: a local `Dictionary<ulong, ulong>` populated by every
   `GetBlockTimestampAsync` fetch the method already performs:
   - `versionId` path: caches the requested block's timestamp (line ~333).
   - `versionTime` path: caches every walked block's timestamp (line ~349) — so `updated`
     and `nextUpdate` are **free** there (issue's "reuse timestamps already fetched").
   - A tiny `GetBlockTimestampCachedAsync(rpc, cache, block, ct)` helper does
     cache-hit-or-fetch with the mandatory cancellation pattern (token check BEFORE the
     call, `.WaitAsyncObserved(ct)`, token check AFTER the await — PR #122 lessons; the
     final pre-success gate at line ~394 already exists and stays).
2. **Populate `Updated`**: when `lastChangeBlock > 0` (exactly when `VersionId` is set),
   fetch/lookup its timestamp → `Updated = <UTC DateTimeOffset>`. Costs at most one extra
   `eth_getBlockByNumber`: on the default path always one; on the `versionId` path zero when
   the requested block IS the last change, one otherwise; on `versionTime` zero.
3. **Populate `NextUpdate`**: when `nextVersionId` is set, fetch/lookup its timestamp →
   `NextUpdate = "yyyy-MM-dd'T'HH:mm:ss'Z'"` (invariant culture, seconds resolution — the
   reference format). Zero extra fetches on `versionTime`; one on `versionId` queries.
4. **Bounded timestamp conversion helper**: `(long)ts` + `FromUnixTimeSeconds` is used
   today at lines 335/358 — a hostile node returning `> long.MaxValue` wraps negative
   (silent 1969 dates) or throws `ArgumentOutOfRangeException`. Add one helper that rejects
   unix seconds `> 253402300799` (DateTimeOffset max) with `EthereumInteractionException`
   (→ existing `internalError` mapping) and use it at the two existing sites and the new
   ones — same-consumer sibling hardening (lessons: enumerate sibling fields reaching the
   same consumer); genuinely tiny.

The deadline CTS already spans these fetches (they're inside `ResolveFromChainAsync`,
bounded per-await); timestamps are `ulong`s so the retained-byte budget is unaffected.

## Review round 1 — 2026-08-01

Reviewer (maintainer) blocking comment on PR #126:

1. **Serialized/exposed representation not canonical (blocking, High for the parity claim).**
   `Updated` is `DateTimeOffset?`, so default STJ rendered `"updated":"…+00:00"` beside
   `"nextUpdate":"…Z"`, and `ToPropertyDictionary()` exposed a `DateTimeOffset` object; the
   14/14 claim was semantic-only. **Resolved**: new public
   `CanonicalUtcDateTimeOffsetJsonConverter` in `NetDid.Core.Serialization` (writes
   `yyyy-MM-dd'T'HH:mm:ss'Z'`, whole seconds; reads any ISO 8601 offset form) applied to
   `Created`/`Updated`/`VersionTime`; `ToPropertyDictionary()` now exposes canonical strings;
   ethr's private formatter delegates to the one Core definition. Pinned by
   `Issue117MetadataCanonicalTimestampTests` (Core, 5 tests: reviewer's exact repro, round-trip,
   offset-normalizing read, property map, sub-second truncation) and
   `Issue117_SerializedMetadata_MatchesReferenceResolverShape` (ethr, end-to-end through
   ResolveAsync). Fail-first: pre-fix model → 2 Core + 1 ethr tests red; restored green.
   Live re-verification now compares the **serialized** `updated` extracted from default STJ
   output: 14/14 DIDs match the reference resolver's recorded values (one transient public-RPC
   flake on retry). Behavior change documented in CHANGELOG (dictionary value types,
   `+00:00`→`Z`).

2. **README genesis wording contradiction + missing `versionId=0` pin (Low).** **Resolved**:
   README and PRD §8.5 now distinguish the unregistered no-events case (omits all four) from a
   `versionId=0` query on a DID with history (omits `versionId`/`updated`, reports
   `nextVersionId`/`nextUpdate`); new `Issue117_VersionIdZeroWithHistory_OmitsUpdatedButReportsNextUpdate`
   pins the four-field shape including the `nextUpdate` string.
