## Context for implementation

PR #108 remains on `feat/issue-107-ethr-write-path`. Review round 2 found two
confirmed defects:

1. `TransactionPipeline` knows the raw transaction hash before calling
   `eth_sendRawTransaction`, but only exports it when the node returns a mismatched hash.
   Connection loss during the send response, receipt-poll failure, caller cancellation, and
   the write deadline can therefore leave an accepted transaction with no queryable hash.
   The current forged-echo fix also inserts a merely accepted transaction into
   `LandedTransactionsKey`, whose public contract says receipt-confirmed.
2. The new required `chainId` parameter on `Erc1056Registry.DeployAsync` is missing from
   the packed README, the PRD source of truth, and an earlier CHANGELOG signature.

Severity: **High** for ambiguous transaction evidence (unsafe retry/double-apply risk);
**Medium** for the shipped documentation/API mismatch.

Out of scope:

- Transaction replacement, fee bumping, and nonce management beyond reporting the locally
  known candidate hash. Those are wallet policies, not evidence propagation.
- Changing ERC-1056 operation ordering, signing formats, or resolution behavior; the defects
  are confined to transaction lifecycle evidence and documentation.

## Adversarial follow-up

The first independent pass was correctly **blocking**. Three agents independently confirmed
that the initial implementation still trusted RPC-controlled `Exception.Data`, accepted a
receipt whose hash was not bound to the submitted bytes, started the deadline after pre-flight,
misreported unrelated `OperationCanceledException` instances as that deadline, and could place
one duplicate hash in both evidence sets.

The revised implementation:

- carries lifecycle state through a private typed `TransactionAttemptEvidence`, never through
  dependency-controlled exception metadata;
- accepts receipt confirmation only for the canonical locally computed submitted hash;
- starts the linked deadline before chain/owner pre-flight and uses `WaitAsync` around
  injectable RPC/signer tasks;
- reports the deadline only when its token actually fired;
- makes confirmed evidence dominate and remove an identical in-flight candidate;
- narrows documentation for validation/pre-flight failures that have no transaction hash.

The second independent pass then found three more boundary gaps: completed dependency tasks
could race cancellation and allow another operation to broadcast, the deadline ended before
post-write readback, and `DeployAsync` did not consume pipeline evidence. The final revision
adds explicit cancellation checks at operation/broadcast boundaries, spans submission plus
post-write readback with the same deadline, and exposes the same evidence sets for ambiguous
deployment failures.

A final hostile-exception attack found that a virtual, throwing `Exception.Data` could still
interrupt evidence projection. Evidence now attaches only to fresh library-owned exception
carriers, while the original dependency exception is retained as the inner cause.

A follow-up correctly noted that `Exception.Message` is virtual too. Carrier construction and
mid-batch formatting now avoid virtual diagnostic properties on dependency exception types.

Focused adversarial regression result after those changes: **19/19 passed** in Release.
