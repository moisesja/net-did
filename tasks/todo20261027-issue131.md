# Issue #131 — did:webvh read-side future-skew bound on versionTime

## Context

did:webvh v1.0, Read (Resolve), step 4, which I checked against the spec source in `decentralized-identity/didwebvh` `spec-v1.0/specification.md:455-459`, says:

> The `versionTime` of every entry **MUST NOT** be more than a small, implementation-defined tolerance in the future relative to the resolver's current time. Resolvers **SHOULD** use a tolerance of no more than 5 minutes. Entries that exceed this tolerance **MUST** cause resolution to fail.

NetDid never compares an entry's time to the clock. `LogChainValidator.ValidateVersionTime` (`src/NetDid.Method.WebVh/LogChainValidator.cs:261-267`) only checks that each entry is later than the one before. As a result, a log dated days or years in the future resolves in NetDid even though conforming resolvers must reject it. Severity is Medium: it is a MUST-level conformance gap, not an authentication bypass. The user wants it fixed in 3.2.0. Nothing is in production, so there is no compatibility constraint.

Other facts from the assessment:
- **Spec steps 10–11.2.** A request for an earlier version (`?versionId=` / `?versionTime=`) that points at a valid entry still returns that version, *even if later entries are invalid*. NetDid already validates only up to the requested version (`DidWebVhMethod.cs:298-301`). The deactivation check over the rest of the log already ignores failures (`:451`), so it does not assert `deactivated` when that later part is invalid. A future-dated later entry falls into this existing path. **No design change is needed there.**
- **Since #127/#132, NetDid never writes a `versionTime` later than its own clock.** It waits at most 2 s, otherwise it fails (`DidWebVhMethod.cs:889-925`). Step 4 of the issue ("write bound ≤ read tolerance") is therefore already satisfied.
- **Caching.** `CachingDidResolver` stores only successful results (`src/NetDid.Core/Resolution/CachingDidResolver.cs:40-41`), which meets the spec's "SHOULD NOT cache a DID that fails verification". A log that is temporarily too far in the future is not cached as an error.
- **No other callers.** Nothing in `samples/` or `tools/` calls the validator.
- **Resolution metadata.** did:webvh does not emit `nextVersionId`/`nextUpdate`, so later entries cannot leak into it.

**Out of scope:**
- The time taken from the clock when *writing* entries (`GetNextVersionTimeAsync`) is already correct.
- Proof `expires` is deliberately evaluated at the entry's `versionTime` (`LogChainValidator.cs:325`).
- `WitnessValidator` does not read `versionTime` against the clock.
- did:key, did:peer and did:ethr do not have this rule.

## Design decisions

1. **One check, in one place.** Add `ValidateVersionTimeNotInFuture(versionTime, now, version)` to `LogChainValidator`. It runs in the loop of `ValidateChainWithPerEntryParamsAsync` for the first entry and for every later entry it validates, next to `ValidateStateScidConsistency`. It runs before the entry hash and proof checks, so the first offending version fails cheaply. Update and Deactivate share the same validator, so they enforce the rule automatically.
   - The rule is `versionTime - now > tolerance` → throw `LogChainValidationException`.
   - This is a subtraction, so it cannot overflow even for a year-9999 entry.
   - An entry exactly at the tolerance is accepted, matching "MUST NOT be *more than*".
2. **The tolerance is fixed at 5 minutes and cannot be configured.** It is an internal constant, `LogChainValidator.MaxVersionTimeFutureSkew = TimeSpan.FromMinutes(5)`.
   - Raising it would break the spec's SHOULD.
   - Lowering it only rejects logs that other conforming resolvers accept, because NetDid's writer never writes future times. The only effect would be less tolerance for clock differences between hosts.
   - Not adding a setting keeps the change free of new public constructor or `AddDidWebVh` overloads. One can be added later without breaking anything if someone needs it. *(If you want it configurable now, say so at approval.)*
3. **The resolver's current time is passed in explicitly.**
   - `ValidateChainWithPerEntryParamsAsync(entries, upToCount, DateTimeOffset now, ct)` and `ValidateChainAsync(entries, DateTimeOffset now, ct)` take `now` as a parameter. The validator never reads a clock in production.
   - The existing `ValidateChainAsync(entries, ct)` stays as a documented shortcut that uses `TimeProvider.System`, so the ~28 existing test call sites do not change.
   - `ValidateChainAsync(entries, upToCount, ct)` has no callers left after this change, so it is removed. The class is internal.
4. **Read the time once per operation, from the existing `Clock` seam** (`DidWebVhMethod.cs:45`).
   - **Resolve:** `var now = Clock.GetUtcNow();` runs once, after the log is fetched and parsed. Both validation passes use it: the pass up to the requested version (`:300`) and the pass over the rest of the log (`:412`). Two passes in the same resolution therefore cannot disagree at the boundary, which follows the lessons' one-ledger-per-resolution rule.
   - **Update/Deactivate:** read the time once before `ValidateChainAsync` (`:546`, `:783`).
   - The `Clock` doc comment changes from "authoring clock" to also cover the resolver's current time.
5. **Errors.**
   - Resolution returns `invalidDidLog` through the existing `LogChainValidationException` catch (`:506`).
   - Update and Deactivate throw `LogChainValidationException`, as they already do for any invalid supplied log.
   - Message: `versionTime at version N is more than 5 minutes ahead of the resolver's current time.` It contains only the version number, with no input text echoed back.
   - **Behavior change for Update/Deactivate:** a head entry more than 5 min ahead used to fail with `ArgumentException` ("aggregate authoring wait"). It now fails earlier with `LogChainValidationException`, because the log is invalid at that moment.
   - A head between about 2 s and 5 min ahead still fails with `ArgumentException`. The existing #127 test with a head 2 minutes ahead (`LogChainValidatorTimestampTests.cs:213-249`) keeps passing unchanged and pins this.

- [ ] New `tests/NetDid.Method.WebVh.Tests/Issue131VersionTimeFutureSkewTests.cs` with `Issue131_*` tests. They drive `DidWebVhMethod` with a fixed `Clock`, so they compile against the pre-fix code and fail on an assertion:
  1. Latest resolution at exactly +5:00 is accepted; at +5:00 + 1 s it returns `invalidDidLog`. Fixtures are written at fixed 2026-07-10 times and the resolver clock is frozen relative to them; whole-second writing means 1 s is the smallest step. Both sides of the boundary are pinned, per the lesson on pinning constants.
  2. A first entry that is too far ahead is rejected.
  3. A later entry that is too far ahead is rejected, while the earlier entries are fine.
  4. A year-9999 entry is rejected with no overflow. Built by hand-signing an entry, same pattern as `CreateAuthenticatedChainAsync`.
  5. **Historical lookup by `versionId` with a future-dated later entry** succeeds (spec 11.2), with `IncludeLog` returning only the entries up to the requested one. When the future-dated later entry is a deactivation, the result is **not** marked `deactivated`. A control case with the clock caught up shows `deactivated` = true.
  6. A `versionTime` query that selects the future entry → `invalidDidLog`; one that selects an earlier entry → success.
  7. **The injected clock is used, not the system clock.** Write a log at a fixed 2030 time and resolve with `Clock` at 2030 → accepted; the system clock would reject it. Resolve a 2026-07-10 log with `Clock` frozen 6 min earlier → rejected; the system clock would accept it.
  8. **The clock is read once per resolution.** A counting `TimeProvider` shows `GetUtcNow` is called exactly once when both passes run.
  9. **Update and Deactivate** (Theory) on a supplied log more than 5 min ahead throw `LogChainValidationException` with the skew message, and the clock does not move.
  10. **Round trip:** a burst of updates written by NetDid resolves on the same clock, with a resolver clock 4 min behind (accepted) and 6 min behind (rejected).
  11. The `ValidateChainAsync(entries)` shortcut rejects a year-9999 entry against the real system clock.
