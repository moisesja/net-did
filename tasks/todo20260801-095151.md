# Issue #116 — did:ethr: RPC infrastructure failures resolve as `notFound` instead of `internalError`

## Context

`DidEthrMethod.ResolveCoreAsync` fails closed correctly (no truncated document is ever returned), but its catch-all ([DidEthrMethod.cs:160-164](src/NetDid.Method.Ethr/DidEthrMethod.cs#L160-L164)) converts **every** failure inside the chain-walk — pruned/hostile-node detection (`EthereumInteractionException`), raw transport errors (`HttpRequestException` escapes `DefaultEthereumRpcClient.SendAllowingNullResultAsync` unwrapped), internal deadline/per-request timeouts (`OperationCanceledException` where the caller's token is NOT canceled), and any parse escape — into `notFound`.

Per the W3C DID Resolution spec (verified against https://www.w3.org/TR/did-resolution/): `NOT_FOUND` means *the input DID does not exist*; unexpected resolver errors "MUST return" `INTERNAL_ERROR`. The library (and the reference `ethr-did-resolver` ecosystem) uses the camelCase registry vocabulary (`notFound`, `invalidDid`, …), so the correct code here is **`internalError`** — exactly what the issue requests. Severity: **Medium-High** (callers treat `notFound` as authoritative "DID never existed" and may reject credentials/purge caches when the correct reaction is "retry against an archive node").

Note: a genuinely unregistered did:ethr identity never errors at all — `changed() == 0` yields the ERC-1056 genesis document. So *every* failure inside the RPC-consuming `try` block is infrastructure, never a statement about the DID's existence.

### Out of scope (with justification)
- **`FindNetwork` failure → `notFound`** ([DidEthrMethod.cs:129-135](src/NetDid.Method.Ethr/DidEthrMethod.cs#L129-L135)): unconfigured network is resolver *configuration*, not an RPC infrastructure failure; the reference resolver uses a distinct `unknownNetwork` code. Changing it belongs to the #120 interop work — will be noted in the PR body, not changed here.
- **Identifier parsing → `invalidDid`**, **options parsing → `invalidOptions`**: already spec-correct; issue confirms.
- **Update/Deactivate read-back** ([DidEthrMethod.cs:642-649](src/NetDid.Method.Ethr/DidEthrMethod.cs#L642)): already guards on *any* non-null `Error`, so it is robust to the new code; only its comment wording ("maps … to a NotFound RESULT") needs a touch-up.
- **Other methods (key/peer/webvh)**: no shared code path; their error mapping is untouched.
