# Issue #136 — did:webvh implicit services and DID URL paths

## Context

Issue #136 is a High-severity did:webvh v1.0 conformance gap. The validated log state is
returned unchanged by `DidWebVhMethod.ResolveCoreAsync`, so the method's derived `#files` and
`#whois` services are absent. Separately, `DefaultDidUrlDereferencer` rejects every bare path
without a `service` query, so it cannot apply those services to `<did>/path` or `<did>/whois`.

The v1.0 DID URL Resolution section requires path-based resolution through `#files`, special
`/whois` handling through `#whois`, and controller-defined services to override the defaults. Its
parallel `did:web` algorithm explicitly requires both missing services to be added to that artifact.
The spec does not state equally clearly that ordinary did:webvh resolution output must serialize
the implicit services, but all six pinned reference implementations do; materializing them there is
therefore the issue-requested interoperability behavior, not an overstated normative claim. The
services remain derived output and must not be inserted into or signed as DID-log state.

## Out of scope

- Fetching and validating the bytes at an external resource URL remains a caller/transport concern;
  the existing dereferencer contract returns a `text/uri-list` service-endpoint redirect.
- `did:key`, `did:peer`, and `did:ethr` documents gain neither synthesized services nor conventional
  bare-path routing; dispatch is explicitly gated to `did:webvh`.
- Create/update DID-log state remains byte-for-byte controller-authored and signed. Implicit services
  are derived resolver output and are never persisted into the verifiable history.

## Review

### Outcome

- Successful current and historical did:webvh resolution projects missing `#files` and `#whois`
  services without changing signed log state or Create/Update result documents.
- Parallel `did:web` artifacts receive the same missing services and rewrite subject-bound absolute
  did:webvh service ids to their did:web equivalents; explicit services remain authoritative.
- did:webvh paths route through `#files`, with exact `/whois` routed through `#whois`. Redirects are
  constrained to the controller-selected HTTP(S) authority and deployment resource base, ignore an
  injected `relativeRef`, preserve endpoint-fragment precedence, reject URI-list controls, and do
  not change bare-path semantics for other DID methods.

- Bare conventional service ids (Medium): aligned implicit-service deduplication with Core's bare-id

  method-name comparison.
- WHOIS confirmation: exact `/whois` selects `#whois`; a query does not alter that parsed path, while

  `?service=` and `?serviceType=` `relativeRef` queries by applying fragments as URI components after
  RFC 3986 path resolution, rather than concatenating fragment text. A final pass also reproduced
  a caller-mutated URI set becoming empty after construction; conventional path resolution now
  snapshots the set and fails closed with `invalidDid` when the snapshot is empty.
